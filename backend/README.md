# Backend

Java 25, Spring Boot 4.1.1, Maven 3.9+, PostgreSQL 18.6. `domain` contains pure policy, image validation and movement rules; `application` coordinates permission checks and idempotent commands through ports; `persistence` implements PostgreSQL transactions and private files; `web` adapts HTTP/session/CSRF/STOMP. Wire fields and errors follow `../contracts/README.md`, `../contracts/accounts.md`, `../contracts/scenes.md`, `../contracts/assets.md` and `../contracts/tokens.md`.

Run unit tests without a database: `mvn test`. Package: `mvn package`. Start: `mvn spring-boot:run` or `java -jar target/dnd-roll-backend-0.1.0-SNAPSHOT.jar`.

Configure `DATABASE_URL` (JDBC URL), `DATABASE_USERNAME`, `DATABASE_PASSWORD`. Flyway applies V1–V5 to an empty database and upgrades existing installations; do not edit previously applied migrations. V3 adds multiple scenes/current selection; V4 adds private assets, map calibration and independent asset command receipts without changing existing rows. HTTP listens on port 8080. Configure `SESSION_COOKIE_SECURE=true` behind production HTTPS. Use a same-origin reverse proxy; the development frontend proxies `/api` and `/ws`.

For a normal installation, set both `BOOTSTRAP_USERNAME` and `BOOTSTRAP_PASSWORD` once to initialize the first account, or omit both. Partial or invalid configuration fails startup. Usernames match `[a-z][a-z0-9_-]{2,31}`; passwords need at least 12 characters and at most 72 UTF-8 bytes, preserving spaces. Bootstrap only inserts a missing account: restarts never reset passwords or campaign permissions. The initial account has no global campaign access. Any authenticated account can create a campaign with an empty 24×16 scene and becomes its DM. There is no unrestricted public registration; further fixed accounts register through an active DM invitation, then log in normally.

DM invitations contain 32 cryptographically random bytes, returned once as unpadded Base64URL. The database stores SHA-256 only. Invitations expire after seven days; previews and registration are anonymous POSTs that still require CSRF. Share the token in a frontend URL fragment, never a backend URL. Retrying invitation creation returns the original metadata with `token:null`; a lost link must be revoked and replaced. Lists expose no token or hash. Accepting an invitation is atomic and single-use; existing DMs keep their role. Removing a player clears only this campaign's control grants, closes all the account's existing sockets after commit, and preserves their account and other campaigns. A consumed invitation cannot restore removed membership.

Campaign management has an independent `campaignVersion`; removing a member also advances affected token/scene versions because their control grants change. Other membership/invitation commands leave movement versions unchanged. Management commands recheck current DM access before durable receipt replay, compare `expectedVersion`, and serialize on the campaign row shared with movement. Creation and management also serialize request IDs on the actor row using PostgreSQL `FOR NO KEY UPDATE`, allowing concurrent invitation foreign-key checks. Membership/invitation changes increment campaign version once; no-ops and retries do not. Removed membership is checked before replaying an earlier move receipt. Old removal receipts cannot remove membership granted by a later new invitation.

Demo setup remains explicitly opt-in: set `SPRING_PROFILES_ACTIVE=demo`, `DEMO_DM_USERNAME`, `DEMO_DM_PASSWORD`, `DEMO_PLAYER_USERNAME`, `DEMO_PLAYER_PASSWORD`. Usernames default to `dm`/`player`; both passwords are required. Demo scene data and permission grants are seeded only when the campaign is first created. Restarts preserve positions, revoked membership and revoked control. Changing an environment password does not reset an existing password.

Run real PostgreSQL integration tests against an **isolated test database** using `TEST_DATABASE_URL`, `TEST_DATABASE_USERNAME`, `TEST_DATABASE_PASSWORD` and `mvn -Pintegration verify`. Missing configuration fails the suite; tests are never silently skipped. P01 tests clean up their own fixtures and keep M1 demo identities separate. Unit `test` does not execute `*IT` classes. Actual RED/GREEN evidence is in `TDD.md`.

Every move locks its campaign row, checks membership and token visibility/control, and replays a matching receipt before checking token version. Token movement, token/scene version changes and its receipt commit in one transaction. A different token or payload with the same key conflicts. Current visibility/control is checked again before replay. Scene versions order snapshots; token versions detect conflicting edits.

STOMP accepts authenticated session connections with current CSRF tokens and subscriptions only to `/user/queue/scene-changes`; client SEND is refused. Events contain only campaign invalidations, addressed individually to current members after commit. Clients recover missed notifications by requesting snapshots.

DMs can create scenes without switching and explicitly select the group's current scene. All scene creation/switch commands share campaign management versions and independent durable scene receipts. Current-scene snapshots remain the sole shared play state; inactive-scene movement and its receipt replay return 404.

P02b stores private PNG/JPEG originals and DM map calibration. Set `ASSET_STORAGE_ROOT` to a persistent directory outside public/static roots, writable by the server account. The local default is `.runtime/assets` relative to the process working directory (Git-ignored); Compose explicitly uses `/var/lib/dnd-roll/assets` on a dedicated volume. Backups must eventually include both PostgreSQL and this directory; full backup/recovery tooling remains P09.

Uploads require multipart `command` JSON plus one image `file`, at most 10 MiB, dimensions 1–8192 and at most 32 million pixels. Actual PNG/JPEG format and complete decoding are checked before original bytes are published atomically under an independent random storage key. Metadata, campaign version and receipt then commit together. After a publication/database/commit error, a fresh campaign lock waits for the original transaction to finish and checks the candidate asset ID and storage key before cleanup. Confirmed rollback cleans only new files; a committed upload keeps its file even when its commit acknowledgment was lost. An unavailable recovery database leaves the outcome uncertain: retain the opaque file, report the original error and let the identical request retry recover the durable receipt. Unknown outcomes and process crashes can leave unreferenced files; no metadata means no download access. There is no automatic deletion in P02b.

All five asset/map routes recheck current DM membership, including downloads and historical retries. Downloads carry `no-store, private`, attachment and nosniff headers on every response and expose neither filenames nor storage paths. Missing/unreadable backing data returns generic 503 `ASSET_UNAVAILABLE`. Uploads use campaign versions; map assignment/detach shares the target scene version with movement and supports inactive scenes. A historical map receipt returns its original response without reapplying old state. Asset commands have a distinct durable namespace and actor→campaign locking. Shared DM/player scene snapshots and events contain no map/image metadata; rendered player maps and Pixi calibration remain P02d. Combat and full backup remain later work.

P02c adds DM-only token listing, creation and full configuration replacement (name, integer position, hidden state and 0–100 exact current member controllers). Tokens are independent of future character sheets. Create shares the scene version with maps/movement; updates share the token version with movement and advance both token and scene versions. A separate global actor/request receipt namespace serializes actor then campaign locks. Authorization and ownership are checked before returning historical receipts; controls are canonical sets and changed payloads conflict. Historical responses never restore older configuration or controls. Member removal removes all campaign grants and advances each affected token and scene once, preventing stale forms from silently restoring grants after rejoin. Hidden tokens stay absent from player snapshots; shared snapshots and invalidation shapes remain unchanged.

V5 backfills token/controller campaign keys, enforces same-campaign scene/token/member foreign keys, and adds durable token receipts. Compatibility defaults fill omitted campaign keys only; explicit mismatches are rejected. V1–V4 migration files remain unchanged. Earlier migration tests explicitly target their original versions; TokenMigrationIT verifies V4 → V5 column/data/checksum preservation and ownership constraints. P02d/e remain pending.

# Backend

Java 25, Spring Boot 4.1.1, Maven 3.9+, PostgreSQL 18.6. `domain` contains pure policy and movement rules; `application` coordinates permission checks and idempotent commands through ports; `persistence` implements PostgreSQL transactions; `web` adapts HTTP/session/CSRF/STOMP. Wire fields and errors follow `../contracts/README.md` and `../contracts/accounts.md`.

Run unit tests without a database: `mvn test`. Package: `mvn package`. Start: `mvn spring-boot:run` or `java -jar target/dnd-roll-backend-0.1.0-SNAPSHOT.jar`.

Configure `DATABASE_URL` (JDBC URL), `DATABASE_USERNAME`, `DATABASE_PASSWORD`. Flyway applies V1 and V2 to an empty database and upgrades existing V1 installations with V2; do not edit previously applied migrations. HTTP listens on port 8080. Configure `SESSION_COOKIE_SECURE=true` behind production HTTPS. Use a same-origin reverse proxy; the development frontend proxies `/api` and `/ws`.

For a normal installation, set both `BOOTSTRAP_USERNAME` and `BOOTSTRAP_PASSWORD` once to initialize the first account, or omit both. Partial or invalid configuration fails startup. Usernames match `[a-z][a-z0-9_-]{2,31}`; passwords need at least 12 characters and at most 72 UTF-8 bytes, preserving spaces. Bootstrap only inserts a missing account: restarts never reset passwords or campaign permissions. The initial account has no global campaign access. Any authenticated account can create a campaign with an empty 24×16 scene and becomes its DM. There is no unrestricted public registration; further fixed accounts register through an active DM invitation, then log in normally.

DM invitations contain 32 cryptographically random bytes, returned once as unpadded Base64URL. The database stores SHA-256 only. Invitations expire after seven days; previews and registration are anonymous POSTs that still require CSRF. Share the token in a frontend URL fragment, never a backend URL. Retrying invitation creation returns the original metadata with `token:null`; a lost link must be revoked and replaced. Lists expose no token or hash. Accepting an invitation is atomic and single-use; existing DMs keep their role. Removing a player clears only this campaign's control grants, closes all the account's existing sockets after commit, and preserves their account and other campaigns. A consumed invitation cannot restore removed membership.

Campaign management has an independent `campaignVersion`; it does not change token/scene movement versions. Management commands recheck current DM access before durable receipt replay, compare `expectedVersion`, and serialize on the campaign row shared with movement. Creation and management also serialize request IDs on the actor row using PostgreSQL `FOR NO KEY UPDATE`, allowing concurrent invitation foreign-key checks. Membership/invitation changes increment campaign version once; no-ops and retries do not. Removed membership is checked before replaying an earlier move receipt. Old removal receipts cannot remove membership granted by a later new invitation.

Demo setup remains explicitly opt-in: set `SPRING_PROFILES_ACTIVE=demo`, `DEMO_DM_USERNAME`, `DEMO_DM_PASSWORD`, `DEMO_PLAYER_USERNAME`, `DEMO_PLAYER_PASSWORD`. Usernames default to `dm`/`player`; both passwords are required. Demo scene data and permission grants are seeded only when the campaign is first created. Restarts preserve positions, revoked membership and revoked control. Changing an environment password does not reset an existing password.

Run real PostgreSQL integration tests against an **isolated test database** using `TEST_DATABASE_URL`, `TEST_DATABASE_USERNAME`, `TEST_DATABASE_PASSWORD` and `mvn -Pintegration verify`. Missing configuration fails the suite; tests are never silently skipped. P01 tests clean up their own fixtures and keep M1 demo identities separate. Unit `test` does not execute `*IT` classes. Actual RED/GREEN evidence is in `TDD.md`.

Every move locks its campaign row, checks membership and token visibility/control, and replays a matching receipt before checking token version. Token movement, token/scene version changes and its receipt commit in one transaction. A different token or payload with the same key conflicts. Current visibility/control is checked again before replay. Scene versions order snapshots; token versions detect conflicting edits.

STOMP accepts authenticated session connections with current CSRF tokens and subscriptions only to `/user/queue/scene-changes`; client SEND is refused. Events contain only campaign invalidations, addressed individually to current members after commit. Clients recover missed notifications by requesting snapshots. This implements exploration movement plus P01 accounts/invitations/members; combat, map assets, scene authoring and backup remain later work.

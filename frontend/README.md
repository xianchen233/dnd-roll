# Frontend

React + TypeScript + native PixiJS tabletop. Same-origin `/api` HTTP requests carry session cookies and CSRF; STOMP uses `/ws` and the personal scene-change queue. Realtime events only trigger authoritative HTTP refreshes.

```powershell
npm ci
npm test
npm run build
npm run dev
```

Open Vite's local URL. Development proxies `/api` and `/ws` to the Spring Boot service at `localhost:8080`. Without the backend the real login page is still available; account login requires a running backend. Obtain a provisioned fixed account or an invitation from the host. No account password is embedded in the client.

Every authenticated account can create a campaign, even with an empty campaign list. A new campaign opens an empty map. DM campaigns show scene and members/invitations panels. Creating, revoking, and removing use a UUID request ID plus the loaded campaign version; a conflict refreshes the management lists before a new attempt. Uncertain network failures offer retry with the original request. PLAYER campaigns do not show or fetch DM preparation or invitation management.

DMs can create named empty scenes without activating them, then explicitly switch the whole campaign. Scene commands reread the shared P01 campaign version before each new action, preserve the exact request for explicit retry on transport/5xx failures, and refresh after 409 without blindly replaying. A concurrent background list read owns only displayed state: it cannot silently cancel the command preflight. The command uses its own preflight version, allowing an explicit server conflict rather than adopting an unrelated newer read. Campaign/API changes and any concurrent authorization denial still invalidate old command work. A successful receipt only acknowledges the command; the map and current-scene list come from fresh server reads. Changing scenes clears selection and failed movement retries, and isolates old movement responses even after returning to the original scene. Map or management 401/403 clears the map and all management panels, including delayed successes. Safe shared maps and manual fog are implemented in P02d; integrated P02e acceptance is recorded in the repository verification log.

DMs author tokens in the current scene with names, integer positions, hidden visibility and multiple member controllers. Creation uses the loaded scene version; editing uses the token version shared with movement. The form waits for both token and member lists before submitting, freezes conflicting edits after ambiguous failures, and retries the identical body/request ID. Historical receipts trigger fresh token and shared-scene reads. Only the newest applicable read started after acknowledgment confirms synchronization; a failed refresh remains explicit and can recover without another POST. Background updates preserve unsaved drafts and their original token version, while removing controls for members who have left. A conflict discards the command and reloads current configuration. Membership changes, realtime hints and the periodic sync refresh the management views as well as the shared scene. When control or visibility is revoked, selected units and pending/retryable movement clear immediately; later old movement responses and later regrants cannot restore that selection or command.

The DM preparation panel uploads private PNG/JPEG assets (up to 10 MiB), lists validated image metadata, and previews/downloads the original through authenticated, noncached fetches. It assigns or detaches a map on the current scene, with image grid size, offsets and per-cell distance. These settings do not change the shared Pixi exploration grid. Play uses a separately authorized, server-calibrated safe PNG; players never request the original asset. Uploads use the latest campaign management version; map commands use the latest target scene version. Uncertain network/5xx failures retain the original File, body and request ID for explicit retry. Deterministic 4xx errors clear that command, 409 refreshes the authoritative state, and historical success receipts never overwrite the current map. If a confirmed command's refresh fails, the panel states that synchronization is incomplete. Scene/campaign changes, logout, and any concurrent 401/403 discard private previews and pending commands, revoke object URLs, and isolate delayed responses.

After an asset command is acknowledged, its own refresh or a newer revision/manual refresh can establish synchronization. Only the latest applicable read started after acknowledgment can do so; earlier reads and historical receipts cannot. A late older read failure cannot erase a newer successful confirmation, and a failed newest read stays explicitly unsynchronized until a later authoritative refresh succeeds, without repeating the POST.

Shared map reads use only current-scene map-view and map-image endpoints with session cookies and cache: no-store. The map-view contains only scene/version and distancePerCell. The server image already excludes covered source pixels; Pixi never hides an original image as a secrecy boundary. Scene invalidations, reconnect, periodic and manual refresh remove the displayed image before reading a replacement, even if that snapshot read fails. URL owners revoke every replaced/disposed blob, and Pixi destroys explicitly owned textures and sources without using the URL/Assets cache. Delayed successes cannot restore old images. Any concurrent 401/403 in the current campaign clears the whole tabletop, including a late image denial from the previous scene; previous-campaign responses are isolated.

The native Pixi toolbar provides pointer pan, cursor-centered wheel zoom, reset and two-point Euclidean measurement multiplied by the configured distance per cell. This is a geometric aid; no D&D combat movement rule is inferred. Resetting or switching tools cancels unfinished gestures and measurements. Same-scene image/snapshot refreshes preserve active drags and measurement pairs while disposing old image resources independently. Scene, selection, token version or control changes cancel the old gesture. The canvas reports interaction readiness only after stage handlers are installed, and image readiness only after image decode completes. DM-only rectangular reveal/cover gestures and integer coordinate fallback modify a shared local fog draft. Explicit save replaces the server's revealed cell set using its original scene version. Background reads keep an already loaded local draft editable while submission waits for fresh data. Concurrent updates preserve a dirty draft's version; ambiguous transport/5xx failures freeze conflicting edits and retain the exact command/request ID for explicit retry. Historical receipts only acknowledge the command; only the newest successful post-ack read confirms current synchronization. Unit hiding and control remain independent of covered map cells. Already delivered public pixels cannot be retracted from a player's saved copies.

An invitation URL uses `/#invite=TOKEN`, never a query or backend path. The DM receives a copyable link only on its first response; replay with `token:null` explains how to revoke the invitation and create a replacement. Links stay in component memory only. Invite visitors can preview anonymously, register a new fixed account, or log in with an existing one and accept. Registration explicitly logs in afterward. Success clears the fragment and opens the joined campaign. If registration succeeded but its response or the subsequent login was lost, the fixed-account login/accept recovery remains available even when preview reports that the invite was already used; the backend rechecks membership. Passwords keep spaces, require 12 Unicode characters, and allow at most 72 UTF-8 bytes.

Select a campaign and a controllable unit, then click a destination grid cell, drag the selected unit with a snapped preview, or submit integer X/Y coordinates in the right panel. Coordinates begin at `(0, 0)`. Uncontrolled units are disabled. The map keeps confirmed coordinates while a command is pending. A network failure offers retry with the original request ID; conflict refreshes the snapshot and asks for a new choice. After a successful move POST, either its own refresh or a newer realtime/periodic refresh can confirm synchronization; reads started before the acknowledgment cannot confirm the move. If synchronization fails, a later successful refresh recovers the saved confirmation.

Connection state refers to realtime transport. HTTP refresh also runs every 15 seconds and after reconnect; this is not an offline editing client. A 401/403 clears the map and any pending command, including older concurrent responses; the campaign-list refresh action lets a removed member switch to remaining campaigns. See [TDD evidence](TDD.md) for executed tests and remaining real-browser validation.

## Real-service browser acceptance

Start the backend with opt-in `demo` data and start Vite before running E2E. The tabletop test expects the seeded `Adventurer` and `Hidden enemy` units, and changes the adventurer's X coordinate by one cell. The P01 test creates a new empty campaign and a unique invited account, removes that member, checks real socket closure and the cleared guest map, then logs the persistent account in again. The P02a test moves a demo unit, creates a preparation scene without activating it, checks player denial, switches both sessions through real STOMP, and returns to the unchanged moved scene. Its cleanup restores the original current scene even after an assertion failure. Use an isolated test database; these tests deliberately write real records.

The fourth test prepares a separate scene, generates a valid PNG in memory, uploads/previews/downloads it through the DM UI, compares downloaded SHA-256, saves calibration, checks player metadata/known ID/guessed ID/direct navigation denial, and verifies configuration after switching away and back. It restores the original current scene in cleanup. No HTTP/STOMP is mocked. Original-image bytes and private map settings remain DM-only throughout this preserved P02b acceptance. Separate P02d cases verify safe shared-image delivery.

Three further cases independently cover P02c, bringing the suite to seven tests. The first uses UI login, campaign creation, invitation, token creation with two controllers and player movement. The second prepares a separate campaign with real CSRF/login and HTTP commands, then uses the UI to hide/reveal and revoke/regrant control while checking hidden snapshots, old movement receipts and cleared selections. The third prepares another independent campaign, removes and reinvites a member through the UI, and checks that historical token and movement receipts cannot restore control. Player snapshots and real STOMP hints contain no hidden token data or controller lists. All three leave the demo campaign unchanged, use real services without mocked HTTP/STOMP or forged sessions, retain the 60-second per-test limit and zero retries, and close their browser contexts in a separate fixture teardown. Screenshots and actual execution results are recorded separately in TDD.md and the repository verification log.

Six P02d cases bring the preserved browser baseline to thirteen cases: player selection/drag/click movement; geometric measurement and partial-pair reset; pan/cursor zoom/viewport reset; DM UI rectangular reveal with decoded public and secret PNG pixels; DM UI cover with original/guessed URL denial, stale URLs and conditional/Range cache checks; and coordinate fallback with an intentionally aborted player snapshot delivery. Movement and both rectangle cases deliberately interleave a real authoritative HTTP read while the native pointer stays held; measurement also interleaves a read between its two points. Measurement and viewport cases use real DM HTTP setup and the player UI, without an unused DM renderer; the other cases retain both UIs. Cover has an independent real HTTP reveal precondition, while UI reveal is verified in its own case. The fallback case proves old image disposal and blob revocation even on refresh failure, then restores real delivery and verifies covered black pixels. HTTP authoring, image generation, sessions and STOMP remain real. Only the fallback case interrupts browser transport reads; it does not fabricate server responses. Each case creates an independent campaign, keeps the 60-second limit and zero retries, and preserves all seven prior cases. P02e composes these behaviors in the four cases below.

The static Pixi tabletop disables its automatic frame ticker and explicitly renders image delivery/removal, token updates, drafts, pointer previews, measurements and viewport changes. Invalidation removes and destroys the old texture and repaints synchronously, including when no new image can be read. No continuous animation is currently used.

Provide `E2E_DM_USERNAME`, `E2E_DM_PASSWORD`, `E2E_PLAYER_USERNAME`, and `E2E_PLAYER_PASSWORD` in the execution environment; every variable is required and passwords have no fallback. `E2E_BASE_URL` defaults to `http://127.0.0.1:5173`.

```powershell
# Use a local Chrome installation, or omit this variable for Playwright Chromium.
$env:E2E_CHROME_PATH = 'C:/Program Files/Google/Chrome/Application/chrome.exe'
npm run test:e2e
```

For CI's bundled browser run `npx playwright install --with-deps chromium` first. `npm run test:e2e:headed` is available for manual observation. The test uses two isolated cookie contexts and real HTTP/STOMP connections, checks player filtering, observes a real DM STOMP invalidation, moves through the UI, reloads, verifies canvas rendering has initialized, and logs out both accounts. It rejects browser JavaScript/console errors except the expected unauthenticated `/api/auth/me` probe. Screenshots and failure traces are written under ignored `test-results/`; the HTML report is under ignored `playwright-report/`.

Four independent P02e cases bring the complete suite to seventeen cases. They compose two-scene fog/calibration preservation and full-cover recalibration, actual player browser offline/online recovery of missed scene/fog and permission changes, and a committed fog POST whose response is deliberately lost before exact-body historical retry. The retry case also interrupts post-acknowledgment reads and requires a successful fresh read before synchronization is confirmed. These tests retain all thirteen earlier cases unchanged. Only the dedicated response/read fault injection uses route interception; the offline cases combine real browser network state with explicit close() on captured native WebSocket instances. Node-side socket-close events and a later new socket with a real STOMP CONNECTED frame prove reconnection; STOMP is never fabricated. Member removal must return 204 and disappear from the member list before the player goes online. Recalibration checks both the real POST target/offset and the read-back configuration.

# A24d typed evidence rebinding and hash regeneration (review only)

This slice follows A24c, covering only its declared A08–A23 record adapters. Read a trusted native archive, matching isolated database and assets in one audited read-only repeatable-read snapshot. Require the unchanged A24b relational proposal and A24c provenance/version/alias/canonical gates before rebinding. No HTTP route, migration, campaign writer, receipt insertion, resource spending or permission grant.

Reconstruct typed records at declared fields. Campaign/card/preview/action/roll identities use their explicit namespaces; event and correction identities use their owner's event namespace. Timeline IDs retain the message/roll/action hard alias. A16/A19 attempt IDs retain their roll alias, and state/journal IDs retain their target alias. Preserve numeric character and independent shared/restabilization ledger versions, including exact originVersion and damageVersion references, with closed historical evidence. Never recursively replace UUIDs or UUID-shaped strings.

Bind derived event identities to the archive digest, proposal seed, source/target campaigns and typed owner; reject collisions with source events, proposed runtime identities, other generated events and occupied SQL UUIDs in the audited database. Metadata in a failure report must also be validated; an invalid digest or adapter name must never echo arbitrary input text.

Preserve free text, timestamps, historical actor/completion actor/controllers, fixed Source and content identity, character-local resource/attack/skill/casting keys. Their preservation is evidence policy, not target authorization. Rebuild only fully canonical annotations with their verified owner and target, using original reviewed values and real roll totals. Unknown shapes, fields, discriminators, references, noncanonical annotations or unsupported adapters block explicitly. Permissions/files/modules and other runtime adapters remain separate follow-up slices.

Verify every saved source hash against the original algorithm and complete source evidence before regeneration. Recompute target hashes using that same algorithm and the complete rebound evidence; A22/A23 include the complete rebound original damage journal and its regenerated hash. Source hash values are provenance only. Dice receipt fingerprints remain source provenance, never new campaign receipts. Pending plans require new target review and authorization even when a historical hash can be reconstructed. Do not reuse an old confirmation or claim a regenerated hash is executable.

Persisted hash coverage is Preview.hash and the six Entry.planHash fields (A17/A18/A20/A21/A22/A23). A16/A19 historical plans may be reconstructed to validate origins. Temporary A13–A15 reviews are absent from these persisted adapters and are not invented from event prose or copied receipts; their regeneration and target confirmation are explicitly outside this slice.

Private typed payloads exist only in memory for validation and future integration. Public reports contain fixed codes, UUID mappings, versions, counts and hash proofs; no cards, sheets, reasons, summaries, account names, credentials or filesystem paths. On failure do not emit partial private payloads or exception messages. Reports always have status BLOCKED and executable=false. A successful consistency result means only the declared JSON/hash slice is consistent. Keep explicit writer, authority and unsupported graph blockers; CAMPAIGN_REMAP/P09/M3 stay open.

The offline CLI accepts only literal REVIEW_ONLY, creates a new output using CREATE_NEW, exits 2 for a review report and 1 for invalid inputs/failure, never 0 for a new campaign. Repeated identical trusted input, proposal seed and target must produce identical report bytes. Reject existing output paths without altering them. Validate with offline units, real PostgreSQL integration tests and all sixteen copied native A08–A23 histories; audit all source rows/assets again after inspection.

Entry point: `io.dndroll.backup.CampaignEvidenceRebindCommand <archive> <assets> <new-report> <source-campaign> <target-campaign> <seed> REVIEW_ONLY`. Database connection is provided through `RECOVERY_AUDIT_DATABASE_URL`, `RECOVERY_AUDIT_DATABASE_USERNAME` and `RECOVERY_AUDIT_DATABASE_PASSWORD`; credentials never enter reports.

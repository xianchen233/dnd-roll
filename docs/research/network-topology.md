# 联机拓扑调研

调研日期：2026-10-18。范围：一名 DM 与固定伙伴，浏览器二维 VTT，包含暗骰、隐藏单位、持久化状态。仅讨论设计，未做网络实测。以下“建议”属于结合本项目需求的工程判断。

## 建议结论

采用单一权威 Java 后端，浏览器通过 HTTPS 与 WSS 连接。云服务器与 DM 电脑运行同一套后端、数据库和素材存储；迁移时改变部署位置与访问入口，无需改造成 WebRTC P2P。WebSocket 本身提供浏览器和远端主机间的双向通信。[WebSocket 协议 RFC 6455](https://www.rfc-editor.org/info/rfc6455/)

| 方案 | 对本项目的影响 | 建议 |
|---|---|---|
| 云端集中式后端 | 不依赖 DM 电脑持续开机；登录、权限、日志与存档集中处理；需要租用和维护服务器 | 默认部署方式 |
| DM 电脑运行同一后端 | 复用全部业务逻辑与存档；DM 电脑关机、断网时全团无法访问；需要处理外部连接入口与家庭上行带宽 | 支持，作为本地部署与迁移目标 |
| DM 浏览器充当 WebRTC 权威主机 | 仍需要信令与可能的中继；增加浏览器主机生命周期、存档和连接管理；DM 关闭主机页面会影响全团 | 当前不采用 |
| 所有浏览器全互联 | 与 DM 隐藏信息、统一裁定需求不匹配；仍要设计权威归属、逐人数据过滤与一致性 | 当前不采用 |

表中运行依赖是部署方式的直接推论，并非性能测试结论。集中式部署不要求 DM 的浏览器一直在线，但服务器本身仍然必须在线。

## P2P 为什么不等于无服务器

WebRTC 的连接协商需要独立信令通道，交换 offer/answer 与 ICE candidates；规范不负责实现信令，通常另建 HTTP 或 WebSocket 服务。STUN 用于发现候选连接信息，不能保证在所有 NAT 和防火墙环境下直连成功。[WebRTC 官方连接指南](https://webrtc.org/getting-started/peer-connections)

不能直连时，TURN 服务器中继实际通信流量。因此即使业务改为 P2P，也可能仍要承担信令服务、中继部署或服务费用与流量成本；不能承诺完全无服务器或必然降低延迟。[WebRTC 官方 TURN 说明](https://webrtc.org/getting-started/turn-server)

本项目的移动、掷骰与回合消息不需要音视频级吞吐；判断上，更值得优先解决的是服务器确认操作、逐人过滤隐藏数据、断线恢复和持久化，而不是提前引入第二套实时通信拓扑。

## DM 本机的访问入口

普通 HTTPS/WSS 的家庭部署必须有可达入口。部署时再依据网络情况选择公网地址与端口映射、可达 IPv6、反向隧道或虚拟组网；不能仅在电脑上启动程序就默认所有伙伴能连接。

作为技术可行性示例，Cloudflare Tunnel 通过本机主动建立出站连接连接到其网络，可发布没有公网 IP 的源站；这说明隧道可作为入口，但也带来第三方依赖。本次不推荐具体运营商或隧道服务，实际地区可用性、访问速度与条款需另行验证。[Cloudflare Tunnel 官方文档](https://developers.cloudflare.com/tunnel/)

固定朋友安装虚拟组网客户端也是可选部署方案，其直连同样受 NAT 影响。Tailscale 官方说明，在无法直连时可退回中继；所以虚拟组网不等于所有流量始终端到端直传。[Tailscale 连接类型](https://tailscale.com/docs/reference/connection-types)

## 拓扑、权威和保密分别设计

- 权威角色由业务设计决定：云后端、DM 电脑上的后端或 DM 浏览器主机都可以承担，但传输协议本身不会自动保证裁定一致。
- 暗骰、隐藏单位和 DM 资料只发给有权限的端点。P2P 加密也无法撤回已经交给玩家客户端的数据；不能将完整隐藏状态广播后依靠 UI 隐藏。
- 连接中断后的玩家重连依赖已保存的状态和版本，而非依赖某个浏览器的内存。换部署位置需迁移应用数据和素材，不能靠换通信协议代替迁移。
- 如果以后加入语音，可以单独评估 WebRTC 媒体方案，游戏状态继续使用权威后端；两者无需绑定为同一拓扑。WebRTC 同时支持媒体与数据通道。[WebRTC 官方连接指南](https://webrtc.org/getting-started/peer-connections)

后三点是本项目架构判断，不表示 WebRTC 天生无法实现权限或存档。

## 用户后续澄清与带宽可行性

用户已明确首版使用服务器，后续可以探索内网穿透联机与 P2P；当前只讨论可行性，不实现第二套联机方式。

内网穿透处理地址和防火墙可达性，P2P 描述端点间数据交换的拓扑。可形成不同组合：DM 本机后端经反向隧道对外提供普通 HTTPS/WSS、虚拟局域网内运行原后端，或另外实现 WebRTC 数据通道。前两者优先复用现有权威服务与存档，WebRTC 方案则需另行评估数据传输和主机生命周期。

以下带宽结论是从数据流推导的工程判断，并非基准测试：

- DM 持有地图并分别发送给多名玩家时，端口映射、反向隧道或 TURN 中继仍需要 DM 上传这些数据；中继不会凭空减少源主机发送的字节。
- 若公开素材已在玩家端缓存、预先安装模组包，或者从独立素材存储下载，可减少 DM 在开团时发送的素材。只有授权玩家可见的素材才能分发，不能为分流而传播隐藏资料。
- 若玩家节点互相分享已获授权的素材分块，可能减少 DM 重复上传，但需增加资源可用性、内容校验和访问控制；这种收益不是仅启用穿透就获得的。
- 低体积的回合与状态消息通常比地图文件更容易满足带宽约束；是否降低上传需求要分别分析这两类数据。

后续最容易验证的方案为同一 Java 后端在 DM 电脑运行并配合可达入口；真正的 WebRTC P2P 保留为独立探索，不把它与该本机部署方式混称为一个实现。

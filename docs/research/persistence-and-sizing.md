# 关机保存、迁移与容量估算

研究日期：2026-10-18。以下区分官方事实、设计建议和未经实测的容量估算；当前不实现代码或部署。

## 官方事实

- PostgreSQL 的 pg_dump 可以在数据库并发使用时生成一致的逻辑备份；归档格式可由 pg_restore 恢复。它只负责数据库，不会自动打包应用上传的图片。参见 [PostgreSQL pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html)。
- PostgreSQL 的逻辑备份适合数据库迁移；跨主版本直接复用原数据目录与逻辑恢复是不同操作，不能把运行目录的随意复制当作通用迁移方案。参见 [PostgreSQL 升级说明](https://www.postgresql.org/docs/18/upgrading.html)。
- Windows 上 Docker Desktop 的 WSL 2 后端有操作系统、虚拟化和内存前提，官方列出至少 8GB 系统内存；这不是本应用自身的内存测量。参见 [Docker Desktop Windows 安装要求](https://docs.docker.com/desktop/setup/install/windows-install/)。

## 设计建议

- 同一套 Java 服务可部署在云服务器或 DM 电脑；前端构建成静态文件，由部署入口提供。Node 属于开发与构建环境，不必作为线上常驻应用进程。
- 每次确认的棋子落点、角色修改、回合切换、骰子结果、裁定、资源及状态变更持久化后，再回复成功和发布状态。拖动预览可不落盘。正常停机排空正在处理的操作；恢复以已确认状态为准，不能依赖关机时才保存内存。
- 待 DM 确认的结算预览也应保存。重启后保留待确认状态，不自动重新掷骰或重复应用结果；用操作身份及应用状态防止重复执行。
- 提供完整部署备份，与模组模板导出分开。备份包含数据库逻辑归档、地图/头像/资料等素材、版本清单及必要配置说明；保留账号归属、角色、回合、日志和战役进度。
- 制作可迁移备份时短暂暂停新写入并等待进行中的操作完成，再生成数据库归档及与之配套的素材清单；上传素材采用不可变文件身份。恢复时验证版本和素材完整性。云端与本机先使用相同数据库主版本，减少变量。
- 跨云端和本机迁移后，只有一份部署继续接受该战役写入；另一份保持停机或只读，避免两边独立推进后无法简单合并。
- 备份保存在运行主机之外才可覆盖云服务到期或磁盘损坏。建议提供手动下载与可配置定期备份，具体频率、保留数和目标位置尚待用户确认；当前不创建任何 Codex 自动化。
- 本机恢复成功只解决保存状态与运行环境，不自动解决朋友从外网连接；公网可达性见网络拓扑研究。

## 容量估算，非实测

假设：一个团，约 1 名 DM 加 4–8 名玩家，2D 地图，数十到约百个场景对象，无内置语音视频、服务端 AI、实时视野重计算或大型素材转换；地图由客户端渲染。角色数量不等于在线连接数量。

| 档位 | CPU | 内存 | SSD | 说明 |
| --- | --- | --- | --- | --- |
| 紧凑试运行 | 2 vCPU | 2GB | 40GB 起 | 需限制 JVM、数据库与上传处理的占用，不作为性能承诺 |
| 建议起步 | 2 vCPU | 4GB | 40–80GB | Java、PostgreSQL 和静态入口共机，为备份与维护保留余量 |

- 无需 GPU。容量按素材与备份增长，不按角色卡数量粗略决定。
- 初始网络估算可按 5–10 Mbps 上行考虑，地图首次同步可能成为瓶颈；是否够快应根据图片体积与加载目标反推。不要把该区间当作通信协议的最低要求。
- 例：6 人同时下载一张 8MB 地图，服务器共需发送约 48MB；10 Mbps 理想情况下约 38 秒，忽略协议开销和竞争。预缩放、压缩、缩略图、浏览器缓存和预加载比增加 CPU 更直接。
- 本机托管时，若还要运行浏览器、通话工具和 Docker Desktop，可将整机 16GB 内存作为舒适的规划起点；这是工程估算，不是最低硬件要求。
- 上线后用一次完整团测量 CPU、总内存、慢操作、备份峰值和地图加载时间，再调整配置。

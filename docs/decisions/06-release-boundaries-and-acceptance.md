## Question

前序能力如何分配到首版、模组与自动化阶段？怎样用一场完整游玩的具体流程验证首版可用，并证明预留接口足以支持后续阶段而无需重写核心数据？

## Comments

- 用户已同意阶段划分：第一阶段完整手动跑团、半自动角色卡、规则检索与填卡、日志、保存备份；第二阶段模组制作/定制/导入导出/选择性更新、DM 一键触发、明确范围内的攻击自动结算和移动预算提示；后续为自动视野、分队地图、条件剧情、文档辅助转换，穿透/P2P 独立验证。
- 用户选择每日自动备份、默认保留最近 7 份，支持手动生成、下载与恢复，迁移前完整备份。
- 用户新增首版团内 RP 文字与机器人记录能力，全部 RP 历史须长期保存。先完成“确定 RP 文字频道、机器人操作与长期记录”再收敛本票；释放本票领取以免同时推进未决依赖。
- RP 与自动初始先攻的新增边界已确认，前序票已解决。本票重新领取，整理出 [完整设计稿 v0.1](../product-design.md)，包含阶段、架构、数据关系、权限、操作流、扩展、备份与 12 个验收场景。
- 当前设计稿供用户整体审阅；细化的界面布局、包格式、接口边界和验收建议不能冒充已经经过产品实现或团测。待整体反馈后记录最终收敛，不自动进入业务编码。
- 用户后续已明确将规则基线改为 5R（2024 修订版）+ 扩展。当前整体设计为 [v0.2](../product-design.md)，先攻及角色卡类别已按新版核验，规则检索、模组依赖和验收同步更新；原 v0.1 仅为历史阶段记录。


## Answer

2026-10-18 用户明确授权开始编写代码，要求整体框架 → 最小单元测试 → 继续实现 → 最终验收，并授权具体分工；随后指定 GitHub 仓库及 frontend/backend/contracts/deploy/docs/CI 目录布局。本票完成从产品设计到实现的交接。首轮范围为仓库框架与最小纵向切片，其余首版业务、模组及发布按实施路线推进。此授权不等于未执行的集成、容器或完整团测已经通过。

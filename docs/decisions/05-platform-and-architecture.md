## Question

固定伙伴如何连接房间、认证和保存进度？根据开发者熟悉度、服务器条件、手机需求、网络与备份要求，是否采用候选的 Java 模块化单体与网页前端架构，实时同步和素材存储如何划分？

- 用户已确认长期在线服务器为主要部署方式，但需支持关机保存，以及云服务到期后将存档迁移到 DM 电脑继续托管。
- 用户要求估算服务器配置，并比较服务器与 P2P 联机。
- 用户已确认固定账号登录、DM 邀请加入战役，暂不做公开注册与找团大厅。
- 用户已确认手机首版支持角色卡、日志、手动资源维护与掷骰，地图操作以电脑为主，不开发独立 App。
- 保存与容量设计研究见 [关机保存、迁移与容量估算](../research/persistence-and-sizing.md)。当前建议每个已确认操作持久化、正常停机排空操作，迁移使用数据库逻辑备份加素材及版本清单，云端和本机只保持一个可写实例。具体备份频率及保留策略尚未确认。
- 容量初估假设为一个团、1 DM 加 4–8 玩家，无内置语音视频、AI 或服务端实时视野重计算；建议 2 vCPU / 4GB / 40–80GB SSD 起步，非实测承诺。带宽按地图大小、人数和目标加载时间反推。
- 技术版本官方条件核实完成，建议基线详见 [技术栈版本调查](../research/stack-versions.md)；尚未实际安装联调。前端采用 React 单页界面，地图直接封装原生 PixiJS，避免首版引入额外渲染包装和 Node 业务服务器，是面向后端开发者的设计建议。
- 网络研究完成，详见 [联机拓扑调研](../research/network-topology.md)。用户随后明确现阶段使用服务器，内网穿透与 P2P 留作后续探索，本轮只讨论可行性，不扩展首版联机实现。
- 用户比较 PostgreSQL 与 MySQL 后明确选择 PostgreSQL；用户两者经验相近，使用过基于 PostgreSQL 的 Kingbase 等数据库。业务主数据库选型已确认，不再将 MySQL 或 SQLite 列为待选首版引擎；初始版本基线沿用研究建议 18.6，实施前复核补丁与联调。

## Answer

1. 用户确认 Java/Spring Boot + React/TypeScript + PixiJS，固定账号与 DM 邀请，电脑完整操作与手机简化操作。用户只熟悉后端，前端方案优先减少额外工具。
2. 用户确认现阶段使用长期在线服务器；同时要求保存、正常关机恢复和未来迁移至 DM 电脑的能力。候选结构收敛为同一权威后端、数据库和素材存储支持不同部署位置，通过 HTTPS/WSS 连接。
3. 版本建议和官方兼容核验见技术版本研究，容量估算及保存迁移设计见对应研究笔记；它们是供最终方案采用的工程建议，未做实际构建、压测或恢复演练，不将建议误记为已实测结论。
4. 内网穿透、本机托管和 P2P 是可行的后续探索方向，首版不实现第二套网络协议或集成穿透工具。本轮讨论需明确：穿透解决网络可达性，减少云服务器开销并不自动降低 DM 上行带宽；带宽取决于素材与同步消息实际由谁发送。
5. 自动备份频率、保留数量和恢复验收归入阶段交付与验收设计；不因为相关数值尚未定而保持网络与技术方向未决。
6. 用户最终确认 PostgreSQL 为首版及云端/DM 本机共同使用的业务数据库。结构化状态与历史进入关系表，可扩展配置与解释快照按条目使用 JSONB，图片等二进制素材使用主机持久目录并由数据库管理引用；不并行维护 MySQL 或 SQLite 业务引擎。
